# ETU-AI

Dans **Paramètres → Modèles → Modèles locaux**, la liste des modèles installés est relue depuis le dossier local à l'ouverture. Le bouton circulaire à côté du dossier relance cette recherche, y compris pour les projecteurs de vision visibles dans l'onglet **Vision / mmproj** ; « Choisir pour moi » sélectionne un modèle adapté au PC.

Assistant local pour les étudiants du BUT Informatique. L'interface et le bridge restent sur `127.0.0.1:8900` et `127.0.0.1:8901`. MAIA-Beacon écoute par défaut sur `127.0.0.1:11343`.

## Démarrer en développement (Windows)

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-app.txt
.\.venv\Scripts\python.exe run_launcher.py
```

Au premier lancement, ETU-AI se présente avec une courte introduction que vous pouvez passer ; elle est désactivée si la réduction des mouvements est demandée. Pendant la préparation, sa mascotte reprend les animations du studio de logo : elle réfléchit, cherche, parle pendant la validation et célèbre la réussite, avec les mouvements désactivés si le système préfère les réduire. L'assistant de configuration vérifie le matériel, propose des modèles GGUF et permet de choisir la version du moteur dans le même catalogue que Configuration → Installation (versions et variantes Windows, Linux et macOS). Vous pouvez aussi configurer un fournisseur API dans une étape intégrée de l'assistant, ou choisir « Plus tard » pour ouvrir ETU-AI sans moteur local. Le parcours reste à la taille de la fenêtre : seul son contenu central défile, et les actions restent visibles en bas, y compris sur mobile. Pendant la préparation, vous pouvez ouvrir ETU-AI et laisser le travail continuer en arrière-plan, ou annuler l'installation ; les modèles déjà présents et les téléchargements partiels sont conservés. Les clés API existantes restent intactes. La préparation de Beacon et le téléchargement d'un modèle pourront être lancés depuis **Configuration → Installation → Réparer**. Après une préparation réussie, ETU-AI s'ouvre automatiquement. Les binaires et dépendances de Beacon sont gérés séparément dans `ai-server` ; voir [sa documentation](ai-server/README.md). Le lanceur ouvre l'interface dans le navigateur. Les releases Windows embarquent Python et les dépendances préparées pendant le build ; l’installation ne requiert pas Internet pour les dépendances, et le raccourci du bureau lance `ETU-AI.exe`. Les modèles restent téléchargeables après installation.

Le lanceur propose trois modes et choisit **Local** par défaut pour permettre à ETU 2 lancé sur `http://localhost:8888` d'appeler le bridge ETU-AI sur `http://127.0.0.1:8901`. Ce mode autorise les origines HTTP locales de développement sans exposer les services au réseau. **Normal** garde les services en boucle locale, mais refuse les origines ETU 2 sur localhost. **Serveur** publie MAIA-Beacon sur le réseau local au port `11343`, tandis que l'interface et le bridge restent locaux. L'API Beacon n'a pas d'authentification : tous les appareils pouvant atteindre ce port peuvent appeler le modèle. Réservez ce mode à un réseau de confiance. Les modes peuvent aussi être choisis directement avec `run_launcher.py --mode local|normal|server`.

Dans **Paramètres → Installation**, ETU-AI recherche automatiquement une release stable de l’application sur GitHub à l’ouverture de la page. **Rechercher des mises à jour** relance cette vérification sans quitter la page. Pour une release authentifiée par Ed25519, **Mettre à jour** télécharge l’installateur avec progression puis demande confirmation avant de fermer ETU-AI et son compagnon s’il est ouvert, puis d’ouvrir l’installation. Le téléchargement manuel reste disponible dans **Téléchargements** et vérifie le digest SHA-256 publié par GitHub. Si la release n’a pas de paquet compatible, l’interface le signale sans proposer une mise à jour inutilisable. La mise à niveau Windows conserve les conversations, la configuration locale et les modèles. Aucun téléchargement ni aucune installation ne démarre sans action volontaire de l’utilisateur. La section **Moteur d’inférence** reste indépendante : elle permet de choisir et réinstaller une version compatible de llama.cpp.

Sous Windows, le dossier d’installation par défaut est `%LOCALAPPDATA%\Programs\ETU-AI`. Les données persistantes restent dans ce dossier : conversations et réglages dans `storage/chats.db` et `storage/app_state.json`, mesures dans `storage/model-performance.jsonl`, Wiki et son index/vectorisation dans `storage/wiki/` et `storage/wiki.sqlite3`, modèles dans `ai-server/models/`, moteur et dépendances dans le dossier indiqué par `ai-server/config.json` (par défaut `ai-server/deps/`). Les clés API chiffrées et l’identité ETU sont enregistrées dans `storage/api_secrets.dpapi` et `storage/etu_identity.vault` ; leur clé de chiffrement dépend aussi du coffre Windows du compte utilisateur. L’installateur met à niveau les fichiers dans le même dossier, conserve `ai-server/config.json` et ne supprime pas les fichiers locaux des modèles ou du moteur. Une installation choisie dans un autre dossier ne migre pas ces données.

Le manifeste Ed25519 lie la version, le nom, la plateforme, l’URL, la taille et le SHA-256 du setup. Les clés publiques sont épinglées dans `integration/updates.py` et l’outil de publication refuse une clé privée qui ne correspond pas à une clé de confiance ; le workflow requiert le secret `RELEASE_SIGNING_PRIVATE_KEY`. Les releases anciennes sans manifeste signé restent en téléchargement manuel et ne sont pas authentifiées Ed25519. Le parcours direct compare les versions numériques et ne télécharge que la release déclarée la plus récente par GitHub ; il refuse donc une version inférieure ou égale à la version installée. Il n’y a pas de date d’expiration du manifeste ni de compteur de version signé conservé localement : la protection anti-retour dépend de la version installée et de la réponse HTTPS de GitHub. Une compromission de la clé privée Ed25519 permettrait de signer un paquet malveillant. Pour faire tourner la clé, ajouter la nouvelle clé à `RELEASE_SIGNING_PUBLIC_KEY_ROTATION_KEYS`, publier un client qui accepte les deux, basculer le secret de signature, puis retirer l’ancienne clé après adoption suffisante.

### Fenêtre compagnon expérimentale

En développement, installez les dépendances dans le même environnement virtuel avec `python -m pip install -r requirements-desktop.txt`, puis démarrez ETU-AI avec le lanceur. Il démarre aussi le compagnon lorsque ses dépendances sont présentes. Le raccourci sélectionné dans **Paramètres → Général → Fenêtre compagnon** affiche ou masque la fenêtre ; sa position et la conversation ouverte restent conservées lorsqu’elle est masquée. Pour ouvrir directement le compagnon pendant le développement, lancez `.\.venv\Scripts\python.exe companion.py --show`. La fenêtre compagnon ouvre directement le chat sans afficher l’assistant de configuration. La position et la dernière conversation sont également enregistrées pour le prochain lancement. Si une discussion ou l’historique ne charge pas, un bouton **Réessayer** permet de relancer le chargement. Le compagnon reste ouvert pendant la veille et recharge son interface lorsque le serveur redémarre. Une seule instance du compagnon peut être active. Ce lancement n’est pas encore intégré à un installateur ou à un service. La disponibilité du raccourci global et de la fenêtre native dépend du système et de ses autorisations ; notamment, macOS peut demander l’accès à l’accessibilité et les environnements Linux Wayland peuvent limiter les raccourcis globaux.

Dans **Paramètres → Fournisseurs IA et clés API**, l'entrée **OpenAI** propose la connexion avec un compte ChatGPT ou une clé API OpenAI. La connexion par compte s'autorise dans le navigateur sur une adresse locale ; les jetons sont conservés dans le coffre système. Après connexion, sélectionnez les modèles à afficher puis enregistrez le fournisseur. Ce mode utilise l'API Responses avec `store: false` et `stream: true` et dépend des droits du compte ChatGPT. La clé API relève de la facturation API OpenAI, séparée du forfait ChatGPT. Le chat textuel et les images acceptées par le modèle sont pris en charge avec le compte ChatGPT ; les outils ETU 2, la recherche Web locale et les fonctions Wiki nécessitant des appels d'outils ne sont pas disponibles dans ce mode. Les fournisseurs compatibles OpenAI acceptent les URL HTTP et HTTPS ; un serveur local sur `localhost` ou `127.0.0.1` peut être utilisé sans clé API si son serveur ne demande pas d'authentification.

Pour les fournisseurs API, la clé est facultative : ETU-AI tente de charger les modèles puis d'envoyer la requête même sans clé. Les API qui exigent une authentification renvoient alors leur erreur de connexion.

Dans le chat, la jauge reprend uniquement les limites restantes présentes dans la réponse du fournisseur (requêtes ou tokens), et expire avec la fenêtre de réinitialisation indiquée. OpenRouter est aussi interrogé pour le quota de la clé active ou, avec une clé d'administration, le solde du compte. Le coût d'une réponse apparaît dans son historique si le fournisseur renvoie un montant par requête ; les seuls compteurs de tokens ne sont pas convertis en prix estimé.

Pour les modèles cloud OpenAI et ChatGPT, le sélecteur du chat affiche les niveaux d'effort annoncés par le catalogue du fournisseur. Il les actualise par `GET /api/models/reasoning-capabilities` lorsqu'ils ne sont pas encore connus. Le choix est conservé par modèle dans le navigateur et appliqué à la prochaine réponse ; la désactivation du thinking n'est proposée que si le niveau `none` est annoncé. Si le fournisseur ne communique aucun niveau, l'interface l'indique sans proposer de réglage arbitraire. Le changement de modèle ne génère pas de notification.

Les modèles cloud configurés sont également visibles dans `GET /v1/models` du bridge ETU 2 et sélectionnables via `POST /v1/models/select` avec leur identifiant `api:<fournisseur>:<modèle>`. Les permissions de lecture et de sélection des modèles restent distinctes.

Dans l’assistant de configuration, choisissez le port local de MAIA-Beacon et vérifiez s’il est libre ou si un service compatible y répond déjà. Pour préparer une nouvelle instance, choisissez un port libre ; si un Beacon est déjà actif, vous pouvez aussi enregistrer son port et ouvrir ETU-AI. Les modèles utilisés doivent être disponibles dans les dossiers de modèles des deux applications. ETU-AI ne démarre ni n’arrête un Beacon externe ; celui-ci reste sous le contrôle de son application. Le port est aussi modifiable dans **Paramètres → Général → MAIA-Beacon** ; si ETU-AI a démarré Beacon, éteignez-le avant de changer de port, puis rallumez-le. Le chat, le bridge et le Wiki utilisent le port configuré. Le mode Serveur expose ce port sur le réseau local.

Dans **Paramètres → Général**, consultez les indicateurs de MAIA-Beacon et réglez le contexte des modèles locaux avec un exemple de contenu, jusqu’à 262 144 tokens. La taille réellement exploitable dépend du modèle et de la mémoire disponible. La carte s’adapte à la largeur disponible et propose des actions pour allumer, éteindre, mettre en veille, réveiller ou redémarrer Beacon ; l’état activé/désactivé est mémorisé après le redémarrage d’ETU-AI.

## Ce qui fonctionne

- Markdown et coloration syntaxique pendant le streaming et dans l'historique : titres, listes, tableaux, citations, liens et blocs de code. Les blocs de code peuvent être copiés ; les blocs SVG proposent un aperçu basculable avec leur source. Le code de l'interface générée est également consultable et coloré pendant la génération. Marked et highlight.js sont inclus localement ; le rendu filtre les éléments HTML et liens dangereux.
- Les groupes de mise en page générés (grilles et flex) s'affichent sur le fond du chat, sans cadre décoratif extérieur. Les éléments conservent leurs couleurs ; `data-surface="panel"` préserve les cartes et panneaux expressément demandés. Le code original reste consultable.
- Réponse textuelle par défaut ; les interfaces sont réservées aux demandes explicites. Le texte autour d'un bloc HTML reste visible. Les mises à jour d'interface s'appliquent une seule fois à la fin de la réponse. Changer de discussion annule le flux actif ; une deuxième génération simultanée dans la même discussion est refusée.
- Chat en streaming et historique SQLite. Les modèles locaux GGUF sont chargés avec le mode reasoning de MAIA-Beacon activé (effort moyen). Quand le moteur transmet un canal de réflexion ou que le modèle émet des balises `<think>`, ce contenu apparaît au-dessus de la réponse dans un panneau repliable qui se ferme au début de la rédaction. Les lectures du moteur local ne bloquent pas l'API pendant la génération.
- Bouton ■ pour arrêter la réflexion ou la rédaction : fermeture de la connexion au moteur, remise à disposition du formulaire et conservation de la réponse partielle dans l'historique. Le changement de discussion interrompt également la génération en cours.
- Gestion Vision / mmproj sur les modèles locaux installés : recherche des projecteurs dans le dépôt exact du modèle, correspondance de variante et de taille, téléchargement avec vérification SHA256, import local GGUF (2 Go maximum), association persistante et rechargement du moteur. Les projecteurs sont séparés des modèles de chat et stockés sous des noms distincts pour éviter les collisions entre dépôts. Les noms génériques ne sont proposés automatiquement que si le dépôt contient une seule variante de modèle. Un modèle textuel ne devient pas vision avec un mmproj ; les imports manuels doivent provenir de la variante exacte du modèle. Pour Ministral 3B Instruct 2512, le dépôt officiel publie `Ministral-3-3B-Instruct-2512-BF16-mmproj.gguf`.
- Pièces jointes via le bouton ＋, glisser-déposer ou collage d'images : PDF avec texte, DOCX, XLSX, TXT/Markdown/CSV/JSON et fichiers de code, ainsi que PNG/JPEG/WebP/GIF. Le contenu des documents est extrait localement ; les images sont adaptées aux API compatibles OpenAI, Anthropic et Gemini et nécessitent un modèle vision. Les pièces jointes restent disponibles dans l'historique récent et sont supprimées avec la conversation. Limites : 6 fichiers, 10 Mo chacun, 20 Mo au total, 100 pages par PDF et 30 000 caractères par document (60 000 caractères de documents dans le contexte). Les PDF scannés sans texte demandent des pages jointes en images ; l'OCR automatique, l'audio, la vidéo et les anciens formats DOC/XLS ne sont pas pris en charge. Si une API distante est active, le contenu joint lui est transmis avec le message.
- Profils d'assistant enregistrables : nom, emoji ou petite image locale, instructions personnelles. Une conversation garde son profil après redémarrage. L'image est réduite à 128 × 128 et enregistrée localement en WebP. Sous Windows, les clés API sont chiffrées avec DPAPI. Si l'ancien coffre est inaccessible depuis le compte Windows actuel, ETU-AI en conserve une copie chiffrée dans `storage/` et crée un nouveau coffre pour les clés saisies. Si DPAPI échoue également à l'écriture, ETU-AI essaie le Gestionnaire d'identifiants Windows.
- Les réponses HTML/CSS et les formulaires sont affichés progressivement dans le chat, avec des styles isolés par Shadow DOM et une source consultable. Seuls les programmes JavaScript utilisent une iframe transparente, sans accès à l'application ni au réseau, et démarrent une fois après la génération. Les formulaires transmettent leurs champs au modèle, y compris les cases décochées, les sélections multiples et le bouton choisi. Les boutons `data-copy` et `data-action` permettent les autres interactions.
- Les zones `data-update-marker` et les marqueurs `<?start name="…">…<?end>` peuvent être modifiés par `<template for="…">` dans une réponse suivante, aussi après réouverture de la conversation. Les marqueurs réservés `chat-canvas` et `chat-style` permettent au modèle de réutiliser une vue et de changer l'apparence de la conversation. La vue occupe la zone de conversation ; un bouton dans l'en-tête permet de revenir à la discussion et d'afficher à nouveau la vue. Les styles sont limités aux messages : la sidebar, l'en-tête et les réglages restent sous le contrôle de l'application. Le Markdown reste lisible.
- Catalogue Hugging Face public sans identifiants, vérification des noms de fichiers avant téléchargement, reprise, annulation et suivi de la progression. Une empreinte SHA256 publiée par Hugging Face est comparée lorsqu'elle est disponible.
- Affichage distinct du matériel conseillé, du modèle chargé et de l'état de veille de Beacon. La présence d'un NPU ne prouve pas son utilisation.

Le bridge ETU 2 utilise une identité Ed25519 protégée par DPAPI, un consentement explicite, des challenges signés, des sessions temporaires liées à l'origine et une révocation. L'outil de lecture de l'EDT donne aussi accès à la carte des salles et des prises. Avec l'autorisation distincte d'écriture, ETU-AI peut créer des événements personnels et les partager avec plusieurs amis ; une confirmation dans le chat n'est demandée que lorsque l'utilisateur la demande ou qu'un choix reste incertain. Les discussions qui attendent une confirmation portent une pastille bleue. Lorsqu'une réponse cite des cours de l'EDT, ETU-AI affiche les cartes interactives selon les couleurs, le texte et les effets des ressources d'ETU 2, avec un lien qui ouvre le cours dans son calendrier. Les cartes restent visibles après rechargement de la conversation. Le modèle local peut utiliser ces outils directement. Pour un fournisseur distant compatible OpenAI comme Mistral, l'envoi des résultats est désactivé par défaut et nécessite l'autorisation explicite dans **Configuration → Connexion ETU 2**. Le protocole est décrit dans [integration/README.md](integration/README.md). L'ancien `/api/handshake` reste désactivé.

## Recherche web

[DDGS](https://github.com/deedy5/ddgs) est référencé comme dépendance Python dans [`external-dependencies.json`](external-dependencies.json) et épinglé à la version 9.16.0 dans `requirements-app.txt`. Il n'a pas besoin d'un service séparé : installe les dépendances de l'application puis redémarre ETU-AI. L'assistant peut effectuer des recherches web générales et d'actualités ; le menu `＋` permet aussi de forcer la recherche pour un message. Les requêtes sont envoyées aux moteurs de recherche utilisés par DDGS.

Le Wiki local est accessible dans **Paramètres → Wiki et mémoire** : documents
Markdown, recherche RAG, historique, graphe et file de traitements persistante.
Le dossier peut aussi être ouvert comme coffre dans Obsidian : les liens `[[...]]`
et les propriétés YAML restent dans les fichiers Markdown standards.
La mémorisation automatique et le partage avec les API distantes sont désactivés
par défaut. **Paramètres → Mes données** permet d’autoriser le partage des passages
du Wiki avec les fournisseurs tiers et de supprimer les documents et leur historique
de révision. L'architecture, les réglages et l'API sont décrits dans [WIKI.md](WIKI.md).

## Vérifier

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
node --check ui/app.js
node --check ui/generative-ui.js
node --check ui/etu-bridge.js
```

Pour vérifier le rendu natif, les marqueurs, les styles et les formulaires dans un navigateur : lancer `python -m http.server 8902 --bind 127.0.0.1`, ouvrir `http://localhost:8902/tests/generative_ui.html`, puis soumettre les deux formulaires de test. La page affiche les résultats `PASS`/`FAIL` ; le compteur du programme doit rester jouable après la mise à jour de sa zone de texte.

Les tests API utilisent une base temporaire pour préserver les conversations locales.
Les commandes d'arrêt et le panneau mmproj peuvent être vérifiés dans `http://localhost:8902/tests/chat_controls.html` avec le serveur statique ci-dessus ; les requêtes y sont simulées et les résultats s'affichent en PASS/FAIL.

Les étapes et critères restants sont dans [ROADMAP.md](ROADMAP.md).

L'interface active est dans `ui/`, servie par ETU-AI sur le port 8900. L'ancien prototype `ui-beta` de Phil Holden a inspiré l'interface et le mécanisme de mise à jour, mais ne fait pas partie de l'application. ### Publication Windows

La publication d’une release GitHub avec un tag numérique comme `v1.2.3` déclenche `.github/workflows/windows-setup.yml`. Le workflow teste le code, puis produit `ETU-AI.exe` et un setup Inno Setup autonome : Python et les dépendances verrouillées dans `requirements-windows.lock.txt` sont préparés dans le build, donc l’installation et le premier démarrage ne requièrent pas Internet ni Python préinstallé. Le smoke test Windows installe le paquet hors ligne, simule une version antérieure, puis vérifie la mise à niveau, les données existantes et le démarrage sans Python sur `PATH`. Les modèles restent téléchargés séparément après installation. L’icône `assets/etu-ai_logo.ico` est intégrée à `ETU-AI.exe`, au setup et à la fenêtre compagnon. Authenticode est facultatif : configurez `WINDOWS_SIGNING_PFX` (PFX encodé en base64) et `WINDOWS_SIGNING_PASSWORD` si vous disposez d’un certificat `etu-aix`. Sans ces secrets, les exécutables sont non signés Authenticode ; le workflow émet un avertissement et ajoute un fichier de statut à l’artefact et à la release. Windows peut afficher un avertissement SmartScreen. Avec un certificat, SignTool horodate et vérifie les deux exécutables. Le manifeste de l’installateur est toujours signé Ed25519 ; le secret GitHub `RELEASE_SIGNING_PRIVATE_KEY` contient la clé privée PEM encodée en base64. Le workflow vérifie qu’elle correspond à une clé publique de confiance intégrée dans `integration/updates.py` et refuse tout build si elle manque ou ne correspond pas. Les anciennes releases sans manifeste restent téléchargeables avec le contrôle SHA-256 GitHub, mais ne sont pas authentifiées par Ed25519. Aucune signature ne garantit qu’un antivirus ne signalera pas le fichier. Fermez ETU-AI avant de lancer une mise à jour.
